# The CUDA modules of pzsolve: one line for each, and the only list of them. Adding a module is a line here and the file <name>.ptx that
# tools/gen_ptx.py writes. The line is read by
#   - tools/gen_ptx.py (what to compile and with which -D options),
#   - the Makefile (which files to embed, and the base of each for the compression), through tools/ptx_table.awk,
#   - the CUDA runtime (src/rt_cuda.c): the table of build/ptx_mods.c says which module an rt_build(program, parameter) call loads,
#   - the simulated driver of tests/mock_cuda: which kernel it runs for a module, and the kernels it has to compile.
#
# name      the module, and the name of its file in this folder
# kind      linear (src/kernels/pz_linear.cl), kang (pz_kang.cl) or test (pz_test.cl); all three come after pz_common.cl
# cfg       what the parameter of rt_build has above bit 16 (src/gpu_priv.h): the minimum resident blocks per SM of a linear kernel plus 8 times
#           its hash variant (PZ_HASH_*, see the end of the file), the configuration of the batch products of a kangaroo kernel (0 at every
#           walker, 1 at every other, 2 at every fourth, 3 one inversion per block: the block herd)
# base      an earlier module whose text is the dictionary of this one in the compressed embedding (src/lz.c), or - for none; the modules of
#           a family differ in few lines, so all the PTX takes about 1 MB instead of 12. A base comes before the modules that use it
# defines   the -D options of the NVRTC build, or - for none. The size of the parameter of rt_build (HALF, or NK) is the value of -DHALF / -DNK
#
# The order matters for the bases only: a base comes before the modules that use it (tools/gen_ptx.py compiles every module in a process of its
# own, so the text of a module depends on its sources and options alone). A new module goes at the end.
#
# name         kind    cfg  base       defines
linear128      linear  0    -          -DHALF=128 -DPZ_FMA_CARRY
linear256      linear  0    linear128  -DHALF=256 -DPZ_FMA_CARRY
linear512      linear  0    linear128  -DHALF=512 -DPZ_FMA_CARRY
# at least 4 resident blocks per SM: the compiler caps the kernel at 128 registers (a few spills, more warps).
# PZ_FMA_CARRY (linear and test modules): the carries out of the addition chains and the normalization of x on the FMA pipe
# (pz_cuda.h); the kangaroo modules keep the forms of 1.17.0
linear128m4    linear  4    linear128  -DHALF=128 -DPZ_MINB=4 -DPZ_FMA_CARRY
linear256m4    linear  4    linear128m4 -DHALF=256 -DPZ_MINB=4 -DPZ_FMA_CARRY
linear512m4    linear  4    linear128m4 -DHALF=512 -DPZ_MINB=4 -DPZ_FMA_CARRY
# kangaroos per work-item (one field inversion per NK steps); capped at 128 registers (four blocks per SM: 512 threads;
# without the cap ptxas uses 150-220 registers and only two blocks fit)
kang64         kang    0    -          -DNK=64 -DPZ_MINB=4
kang128        kang    0    kang64     -DNK=128 -DPZ_MINB=4
kang256        kang    0    kang64     -DNK=256 -DPZ_MINB=4
# the same with the batch products kept only every 2 walkers (less memory traffic, half a product more per step)
kang64b        kang    1    kang64     -DNK=64 -DMC=2 -DPZ_MINB=4
kang128b       kang    1    kang64b    -DNK=128 -DMC=2 -DPZ_MINB=4
kang256b       kang    1    kang64b    -DNK=256 -DMC=2 -DPZ_MINB=4
# batch products kept only for every 4th walker (about 16 bytes less traffic per step): needs more registers than fit in 128
# (about 212 without spills), so only two blocks of 128 threads stay resident per SM; the tuner keeps it only where it is faster
kang64c        kang    2    kang64b    -DNK=64 -DMC=4 -DPZ_MINB=2
kang128c       kang    2    kang64c    -DNK=128 -DMC=4 -DPZ_MINB=2
# smaller herds per work-item (16, 32), for GPUs whose L2 cache can hold the whole herd (the tuner offers them only there)
kang16         kang    0    kang64     -DNK=16 -DPZ_MINB=4
kang32         kang    0    kang64     -DNK=32 -DPZ_MINB=4
kang16b        kang    1    kang64b    -DNK=16 -DMC=2 -DPZ_MINB=4
kang32b        kang    1    kang64b    -DNK=32 -DMC=2 -DPZ_MINB=4
test           test    0    linear128  -DPZ_FMA_CARRY
# the block herd: 4 walkers per work-item, all in registers (250 of them: two blocks of 128 threads per SM), and one inversion per block and
# round for the 32 columns of products of the block (pz_kang.cl, KANG_BLOCK; docs/en/RESEARCH.md section 5)
kang4g         kang    3    kang64     -DNK=4 -DKANG_BLOCK=1 -DPZ_MINB=2
# the hash variants of the linear kernel (pz_cuda.h, RESEARCH.md section 5 after 1.19.2), for the default window and for 512 with the register cap:
# h1 (cfg + 8) computes the two shifts of each sigma of the SHA-256 schedule as mul.hi by a power of two from the constant bank (88 IMAD.HI per key
# off the ALU pipe, which bounds the hash) and folds four small sums of the first rounds onto the FMA pipe (PZ_HASH_FOLD); h2 (cfg + 16) folds the
# same sums and computes the rotation by 10 of every RIPEMD-160 step as the two halves of a product by 2^10 (151 IMAD.WIDE and IMAD per key).
# Neither wins in the issue model at the cost of an IMAD.HI measured on the A2000: they are forceable probes of what an IMAD.HI and an IMAD.WIDE
# cost in the hash, for a card to time once (PZ_GPU_HALF=524544, 786944 and 1311232). The tuner measures them with the six others.
linear256h1    linear  8    linear256  -DHALF=256 -DPZ_FMA_CARRY -DPZ_HASH_SIG -DPZ_HASH_FOLD
linear512m4h1  linear  12   linear256h1 -DHALF=512 -DPZ_MINB=4 -DPZ_FMA_CARRY -DPZ_HASH_SIG -DPZ_HASH_FOLD
linear512m4h2  linear  20   linear512m4h1 -DHALF=512 -DPZ_MINB=4 -DPZ_FMA_CARRY -DPZ_HASH_RMD=2 -DPZ_HASH_FOLD
