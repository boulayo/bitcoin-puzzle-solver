# Architecture

## 1. Modules (`src/`)

| File | Role |
|------|------|
| `common.h`, `util.c` | types, logging (terminal + `log.txt`), formatting, atomic files, memory with error checking |
| `platform.h/.c` | **the only operating-system-dependent point** (POSIX and Windows): binary files with 64-bit offsets, atomic rename, campaign lock, large memory (mmap/THP, VirtualAlloc/large pages), clocks, entropy, console (ANSI sequences, width), Ctrl-C / SIGTERM / SIGHUP / window close, dynamic libraries. The rest of the program is C11 + pthread; a few `#ifdef _WIN32` remain only where the code is specific anyway (`cl_api.c`, `rt_cuda.c`, `sysinfo.c`, `doctor.c`, `util.c`, `common.h`) |
| `../lib/pzcore/` | **the reusable crypto core** (own README): `u256`, `fe` (field), `ec` (curve), `hash`, `address` (Base58Check, bech32, WIF), `hash160_batch`, `perm`, `cpu`, and the lane headers `fev.h` / `fev52.h` and templates in `impl/`; built into `build/libpzcore.a` with nothing from `src/`. The rows below for these files now refer to `lib/pzcore/include/pzcore/` and `lib/pzcore/src/` |
| `u256.h/.c` | 256-bit integers, group order `n` |
| `fe.h` | field `GF(p)` (all `static inline`, so every compilation unit gets the code for its *own* instruction set; multiplication and addition/subtraction in MULX/ADX assembly with a C fallback) |
| `fev.h` | **SIMD-lane** field `GF(p)` (9 limbs of 29 bits, `vpmuludq`): one lane = one independent element; limb bounds documented in the header |
| `fev52.h` | the same interface with **AVX-512 IFMA** (5 limbs of 52 bits, `vpmadd52luq/huq`); `fev_chain.inc` holds the parts common to both (inversion chain, broadcast) |
| `ec.h/.c` | secp256k1 curve: Jacobian/affine sums, `k·G` multiplication with a 4-bit window table, (de)serialization of public keys |
| `hash.h/.c`, `hash_tables.h` | SHA-256, RIPEMD-160, hash160, Base58Check, WIF (scalar reference) |
| `hash_simd.inc` | multi-lane SHA-256 + RIPEMD-160 (GCC vector extensions), included once per ISA |
| `engine_impl.inc` + `eng_base.c` / `eng_avx2.c` / `eng_avx512.c` | CPU engine of the linear search with scalar arithmetic, instantiated per ISA with different flags (`Makefile`) |
| `engine_vec_impl.inc` + `eng_avx2v.c` / `eng_avx512v.c` / `eng_avx512i.c` | CPU engine with curve arithmetic on SIMD lanes (N independent windows per round); `eng_avx512i.c` instantiates it with `fev52.h` |
| `cpu_common.c` | shared tables (`i·G`, `cpu_gmultiples` for tables of any size), engine registry, ISA detection, quick check of every engine (known key), autotune |
| `perm.h/.c` | Feistel permutation with SHA-256 rounds (visiting order) |
| `jobq.h/.c` | interval scheduler (work requests, completion, checkpoint, resume) |
| `campaign.h/.c` | immutable campaign configuration, seed generation |
| `puzzles.h/.c`, `puzzles_data.c` | database of the 160 puzzles (generated from `data/puzzles.csv`) plus the addresses of the emptied puzzles 161-256 (`data/puzzles_withdrawn.csv`) and its verification |
| `campaigns.h/.c` | campaign lock (via `platform.h`), `list` command |
| `eta.h/.c`, `ui.h/.c` | time / probability estimation models and the speed estimator (`rate_est`); rendering of the panel and the status line (pure formatting, no I/O) |
| `bench_tg.h/.c`, `profile.h/.c`, `doctor.h/.c` | joint CPU+GPU comparison (`bench --together` and the first-run tuning), machine profile and remembered steady-state speed, `doctor` command |
| `bsgs.h`, `bsgs_priv.h`, `bsgs.c`, `bsgs_isa.inc` (+ `bsgs_base.c`, `bsgs_x86.c`) | symmetric BSGS: hash table of the baby steps, giant steps in groups, save/load |
| `bsgs_vec_impl.inc` + `bsgs_avx2v.c` / `bsgs_avx512v.c` / `bsgs_avx512i.c` | the same windows of 1024 points, 4 or 8 per instruction (`fev.h`/`fev52.h`); verified against the scalar ones before use |
| `kangaroo_priv.h`, `kangaroo.c`, `kang_isa.inc`, `kang_base.c`, `kang_x86.c` | kangaroo: parameters, DP table, solving, scalar walker round, comparison of the variants (`kang_round_check`) and choice of the fastest |
| `kang_vec_impl.inc` + `kang_avx2v.c` / `kang_avx512v.c` / `kang_avx512i.c` / `kang_avx512i2.c` | kangaroo round on SIMD lanes, bit-identical to the scalar one; walker state in vector form between rounds |
| `kang_spec3.inc` | table of the species and bands of kangaroo schema 3 (coefficient, residue mod 12, zone, share); generated by `tools/research/kspec_table.py` from `tools/research/kang_schema3.txt` |
| `run.h`, `run_common.c` | run context, key found, signals, scheduler loading, reporter (panel, report files) |
| `run_linear.c`, `run_kangaroo.c`, `run_bsgs.c` | orchestration of the three modes, kangaroo self-test and benchmark |
| `gpu.h`, `gpu.c` | GPU: listing and choice of devices, self-test, tuning, linear-search and kangaroo workers. Written against `gpu_rt.h`, so identical for CUDA and OpenCL |
| `gpu_rt.h`, `rt.c`, `rt_priv.h` | minimal GPU runtime interface (context, modules, kernels, buffers, launch) and the combined device list (an NVIDIA card seen by both runtimes is recognized by PCI address and used once) |
| `rt_cuda.c` | CUDA implementation: *driver API* loaded at run time (`nvcuda.dll` / `libcuda.so.1`), embedded PTX modules, context with passive waiting |
| `rt_cl.c`, `cl_api.h/.c` | OpenCL implementation: dynamic loader, kernels compiled from embedded sources |
| `kernels/*.cl`, `kernels/pz_cuda.h`, `kernels/ptx/*.ptx` | **a single kernel source**: OpenCL C, compiled by the OpenCL driver or, through `pz_cuda.h`, by NVRTC into PTX (`tools/gen_ptx.py`, committed files) |
| `sysinfo.h/.c` | CPU/RAM/cache, thread affinity |
| `selftest.c`, `main.c` | self-test, benchmark, command-line interface |

The x86 SIMD engines are optional. When the `Makefile` builds for a target other than x86-64 it defines `PZ_NO_X86_VARIANTS`; the engine
registry (`cpu_common.c`), BSGS (`bsgs.c`) and the kangaroo (`kangaroo.c`) then use only the scalar code.

## 2. Flow of a linear campaign

```
main ─ cmd_hunt ─ creates/loads campaign.conf ─ run_linear
                        │ sched_new (perm + intervals) ─ sched_load (state.dat / .bak)
                        ├─ CPU thread i:  loop { sched_claim → engine.scan → sched_complete }
                        ├─ GPU thread j:  loop { sched_claim → kernel pz_search → hit → sched_complete }
                        └─ main thread: reporter (1 Hz) → terminal, report.txt, status.json, stats.csv,
                                        checkpoint every 60 s
Every hit (CPU or GPU) → run_submit_key: recomputes k·G, compares hash160/pubkey → FOUND.txt → global stop
```

The scheduler hands out contiguous portions of a block (≈ 3 s of work for the CPUs, ≈ 0.35 s per launch on the GPUs, adjusted by the
measured speed). An interrupted worker returns the completed prefix; the rest remains a "hole" in the checkpoint and is taken up first in
the next session.

## 2b. Flow of BSGS

```
run_bsgs ─ bsgs_params_init (c, T, S, A, Ng) ─ run_load_sched (giants 1..Ng, same scheduler as the linear search)
         ├─ "driver" thread: table (bsgs_table_load from --table, or bsgs_table_build with N threads and save)
         │                   → N search threads: loop { sched_claim → bsgs_scan → sched_complete }
         └─ main thread: reporter (phase 1/2 during the table, then giants)
bsgs_scan: 1, 4 or 8 groups of 1024 giants (batch inversion, on SIMD lanes if available) → x coordinates → prefetch → table probe → candidate → check k·G = P → run_submit_key
```

## 3. Flow of the kangaroo

```
run_kangaroo ─ (GPU: opens the devices, NK tuning, self-test) ─ kang_create (interval, base, Q', zones)
             ─ kang_configure (K, dp_bits, table, jumps from seed) ─ kang_load_log (dp.bin)
             ─ CPU thread: kang_cpu_worker_main { round (fastest variant among scalar and lanes, verified) → DP → table }
             ─ GPU thread: gpu_kang_thread { kernel pz_kang_step (NK walkers per thread, up to 64 rounds per launch, jump history in
                                              a buffer of 16 bits per step; d and the DPs are rebuilt by replaying it) → DP/restarts → table }
             ─ reporter: probability of success, DPs in the table, restarts
kang_insert_dps (under mutex): inserts or compares with the existing entry → solve_pair → run_submit_key
```

## 4. On-disk formats

* `campaign.conf`: text `key=value` (`format=1`; since 1.1.0 also `bsgs_entries`, optional: 1.0.x campaigns can still be read); `format` changes only with incompatible changes.
* `state.dat`: text; header `PZSCHED 1`, `cbits`, `v_limit`, `keys_done`, lines `iv start end` (hex), final line
  `crc=` (first 8 bytes of the SHA-256 of the content). Atomic write (`.tmp` → fsync → rename); the previous file, if valid,
  becomes `state.dat.bak`.
* `dp.bin`: `"PZDP4\n"` + SHA-256 fingerprint (start, W, `"PZDPLOG4"`, pubkey) + 32-byte records `{tagk, d[3]}` little-endian
  (`tagk` = 61-bit abscissa ∥ 3-bit type: 0 tame, 1/2 wild on `Q` with sign, 3/4 wild on `3Q` with sign; `d` = 192-bit signed exponent).
  A file with another `"PZDP"` magic comes from an older layout (versions up to 1.9.0, campaigns with fewer than 256 kangaroos): `hunt` keeps it as `dp.bin.vN` and starts a new log.
* BSGS table (`--table`): 4 KiB header (`PZBSGS01`, SHA-256, `T`, abscissa of `T·G`, checksum) + little-endian 8-byte cells.
* `session.txt`, `stats.csv`, `status.json`, `report.txt`: see [`USAGE.md`](USAGE.md).

## 5. Concurrency and memory

* One mutex for the scheduler and one for the DP table: accesses are rare compared with the work (blocks of seconds, a DP every
  `2^dp_bits` steps). Progress counters are atomic *relaxed*; the stop flag is atomic.
* Each thread allocates its own buffers (no false sharing); threads are pinned to cores with `sched_setaffinity` (Windows: "ideal" processor, a hint to the scheduler).
* The only shared hot writes are the counters; ThreadSanitizer reports nothing on CPU, GPU and mixed campaigns.
* Memory: linear search ≈ a few MiB; kangaroo: `32 bytes × entries` (limit `--mem`) plus ≈ 0.4 KiB per walker.

## 6. Tests and verification

| Level | Where |
|-------|-------|
| Vectors from an independent reference (`tools/ref.py`, pure Python) | `tests/t_core.c`, `src/selftest.c` |
| Field/assembly | `lib/pzcore/tests/t_fe.c` (two builds: C and MULX/ADX); `lib/pzcore/tests/t_fev.c` (AVX2 and AVX-512: limb bounds, extreme values, verified mutations) |
| BSGS, ETA, database | `tests/t_bsgs.c`, `t_eta.c`, `t_puzzles.c` |
| GPU kernel arithmetic | `tests/t_gpufe.c`: the field of `kernels/pz_common.cl` compiled for the host, portable variant and PTX carry-chain variant (with the carry flag emulated according to the PTX ISA), against the CPU on 5 million combinations with all the edge cases |
| Permutation, scheduler, SIMD engines | `lib/pzcore/tests/t_perm.c`, `tests/t_jobq.c`, `t_engine.c` |
| Complete campaigns | `tests/e2e.sh` |
| CUDA path without a GPU | `tests/mock_cuda/`: a **simulated CUDA driver** (`libcuda.so.1` / `nvcuda.dll`) with the same APIs, which recognizes the embedded PTX modules and runs the same kernel sources on the CPU, checking every call (pointers, copies outside the buffers, launch shape, arguments). It verifies all the CUDA host code; the PTX-to-GPU compilation is left to the real driver and is covered by the self-test at startup |
| Windows | `make windows` / `make wintest`: static MinGW-w64 exe, unit tests, self-test and campaigns run under Wine (`tools/verify.sh`) |
| Sanitizer / Valgrind | `make asan`, `make tsan`, `valgrind` (see `docs/en/RELEASING.md`, section "Before every release") |
| Kangaroo parameters | `tools/research/ksim.c` (abstract model) and `pzsolve kstat` (real curve) |

## 7. Roadmap

* OpenCL kernels with 64-bit limbs for AMD (they need hardware to be tuned). Done: CUDA kernel in PTX with carry chains, lane arithmetic with AVX-512 IFMA, BSGS and kangaroo on SIMD lanes.
* SHA-NI for SHA-256 on CPUs that support it.
* Multi-machine distribution with a coordinator. Today: linear search split into fixed shares (`--part`, `split`), kangaroo with `--node` and `merge`; only dynamic balancing between machines is missing.
* Support for uncompressed addresses.
